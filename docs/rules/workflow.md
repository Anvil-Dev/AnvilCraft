# 工作流、错误处理与单元测试

本规范约束任务执行、需求澄清、交付边界、错误处理与测试验证。执行编码任务前先阅读本文全文。

## SKILL 与规范先行

执行编码任务前，必须先探索并阅读适用于该任务的 `SKILL` 文档、项目规范或操作指南，寻找现有工具链与标准做法。

## 编码前澄清与简化建议

禁止在需求存在歧义时静默猜测并自行选择一种方案编码。当指令存在多种合理解释、关键参数缺失或上下文矛盾时，必须先停下来列出可选方案及其权衡，请求用户确认后再执行。若用户指定的实现方案过于繁琐，且存在明显更简洁的替代路径，必须在动手前直接指出并提出简化建议。该流程称为编码前澄清与反驳机制，任何绕过都会导致返工或交付错误实现。

## 指令边界与防滑坡原则

- 严格对齐指令的字面边界：用户询问“有办法吗？”仅解释方案，不直接执行修改；“不要添加/删除 X”仅约束后续行为，不代表回滚或清理既有内容；“阅读某文件”意味着该文件可能存在外部更新，必须重新读取。
- 多轮对话仅回应当前轮次提及的问题，禁止顺带回复上一轮未提及的分支，禁止主动输出“下一步要不要做 X”等额外建议（除非涉及严重安全漏洞或阻塞性错误）。
- 当用户提供包含多个问题的列表时，严格遵循用户输入的原始顺序输出，禁止按工具分片读取的返回顺序打乱输出。用户不可见工具调用的完整原始返回，回答时必须补齐必要上下文。
- 识别连续妥协滑坡：解决故障 X 时，若出现“方法 A1 不可用改用 B1，导致 A2 不可用又改用 B2”的连续打补丁模式，必须立即停止尝试，全面回顾并重新核查最初 A1 不可用的原因是否成立。

## 完整交付与最简实现

- 禁止编写任何占位代码，除非用户明确要求；若用户要求占位，必须留下 `TODO` 标记并写明原因、完成条件和跟踪方式。
- 禁止只编写最小实现或简单转发层，禁止为了节省时间、精力或 token 而交付不完整的结果，必须完整实现用户要求的全部功能点。若需求过大，应先拆分并取得用户确认，拆分后的每个子任务仍须完整可验收。
- 禁止以非当前项目目标为理由交付未完成的代码，禁止把未完成项标记为已完成。计划项对外交付时只有已完成和未完成两种状态。
- 用最少的代码量解决问题：引入新抽象前，优先遵循目标文件周边的既有代码模式与现成 API；禁止过度设计，禁止引入当前需求不需要的抽象、配置、扩展点、框架或兼容层；禁止为仅单次使用的代码创建抽象层；若 50 行代码即可清晰实现的逻辑写出了 200 行，必须重写简化。
- 禁止为不存在的边界情况设计备用回退逻辑，禁止擅自假设功能的预期用户量与使用场景；边界检查必须基于明确的需求、接口规范或数据约束。

## 最小变更与清理边界

- 每一行修改的代码必须直接服务于用户的当前请求。修改存量文件时，严禁顺手重构、格式化或修改相邻但未损坏的无关代码，禁止将针对单文件的修改擅自扩大为跨模块或全仓库重构。
- 保留工作区（working-tree）中与当前请求无关的未提交改动，严禁回滚、清理或格式化请求范围之外的文件。编辑文本文件时保持 UTF-8 编码，并严格保留文件原有的换行符格式（LF 或 CRLF）。
- 修改已有源码或脚本文件时直接覆盖原文件，禁止新建添加 `_v2`、`_new`、`_old` 等后缀的副本文件；禁止在项目目录或用户目录下遗留临时测试脚本与中间文件。
- 必须彻底清理因本次修改而新产生的孤立导入（import）、未使用变量和废弃函数。对于存量文件中原本存在的冗余套话注释或注释掉的废弃代码，仅清理本次修改直接触及的函数或代码块内部；对于未触及的无关区域，仅在汇报时指出，未经用户要求禁止跨范围删除，确保 `git diff` 聚焦干净。

## 错误处理与兼容

禁止编写仅为兼容旧行为、迁就错误状态或掩盖报错的代码。确需兼容旧行为时，必须明确迁移期和移除条件。异常与错误必须被显式处理或向上抛出，记录日志时必须包含上下文信息，禁止出现空的异常捕获块（如空 `catch` 块）或捕获异常后不处理也不记录日志。

## 单元测试与验证规范

- 将任务转化为可验证的测试目标：修复缺陷时优先编写能复现该问题的测试用例，再修改代码使其通过；重构代码时必须确保重构前后既有测试保持通过。
- 验证时先运行覆盖改动逻辑的局部测试或单模块编译检查，通过后再执行更大范围的验证。
- 单元测试仅用于验证代码运行逻辑，必须直接调用被测代码，禁止编写纯源码字符串包含（`contain`）测试。
- 禁止编写用于长期验证某功能已被删除的测试。确认移除功能时，在同一次变更中连同功能代码与对应测试一起删除。
- 禁止编写魔法值测试，包括常量相等性测试、常量计算结果测试，以及特效属性、配置参数等频繁变动的值；测试必须验证其对业务逻辑的实际影响。
- 对于可撤销、影响较小的改动，禁止编写照搬实现逻辑的测试；仅在测试确有验证意义时编写。
