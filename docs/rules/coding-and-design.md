# 编码与设计规范

本规范约束代码结构、命名、抽象、注释与格式。修改类、接口、模块或公开 API 时先阅读本文全文。

## 禁止滥用反射与元编程

业务代码和测试代码中严禁使用反射、运行时元编程或其他绕过正常访问权限的方式（通用逻辑框架、动态类型系统、依赖注入框架除外）。开发中若遇到无法直接获取的对象，必须先排查所有正常入口，向用户说明无法通过正常入口获取的原因并获得确认后方可使用反射；反射逻辑必须限制范围、集中封装并配备测试。编写测试遇到困难时，优先引入合适的测试框架或调整代码结构，禁止使用反射绕过访问限制。

## 命名规范

类型、接口、模块、函数命名应使用简洁、直白的业务词汇组合，避免过长名称和生僻词。同一概念在全局必须使用同一个词，禁止混用。

正例：`ViolationConfig`、`OpenResult`、`ModelRegistry`

反例：`ViolationActionConfiguration`、`MenuOpenOutcome`、`ModelCatalog`

禁止使用仅表示笼统角色、无法体现具体职责的命名后缀，如 `XxxService`、`XxxManager`、`XxxController`、`XxxRuntime`、`XxxHelper`、`XxxUtil`、`XxxCommon`。处理逻辑应放在接口实现层或职责明确的模块中。若语言或框架强制要求此类命名，可遵循框架约定，但必须保持职责单一。

## 面向接口与模块划分

- 语言支持接口、协议、抽象类型或 trait 时，逻辑层应优先面向抽象编程（仅单次使用的简单逻辑除外），具体实现（如 `XxxImpl`、`DefaultXxx`）仅在内部使用。
- 对外只开放外部真正需要使用的接口或类型；无外部调用需求的内容必须放在内部模块、内部包或私有作用域中。
- 包、模块、命名空间应职责清晰，保持单向依赖，禁止循环依赖；禁止过度细分，也禁止将大量互不相关的业务类型塞入同一模块。
- 构造参数较多或包含多个布尔参数的对象时，优先使用该语言惯用的构建器（Builder）、参数对象或具名参数。

## 代码注释规范

- 公开接口、协议、抽象类型必须编写头部简介；其中首次出现的类型、方法、变量需说明设计动机和作用。
- 内部实现、常量和变量通常不写注释，仅在关键逻辑存在歧义时说明。
- 注释必须解释“为什么这样设计”，禁止复述代码表面做了什么。
- 禁止使用行尾注释，所有注释必须独立成行写在代码上方。
- 禁止编写具有时效性或记录需求变更历史的注释。正例：`对象 xx 的扩展方法，注意调用后会修改内部状态`、`优先使用方法 xx 同步更新对象 yy 的 a 与 b 属性`；反例：`于 xx 时间节点需求变化`、`需求为每秒执行一次 yy`、`设计案确认为 zz`。
- 禁止保留注释掉的废弃代码。修改代码时必须同步更新相关注释。

## 代码格式与风格细节

以项目根目录对应语言的代码风格配置（如 `.editorconfig`、`.eslintrc` 等）为唯一标准；Java 项目以 [java-and-gradle.md](java-and-gradle.md) 中的 `style.xml` 要求为准。遇到 Checkstyle 或 Linter 报错时必须直接修复代码，禁止添加抑制注解或注释（如 `@SuppressWarnings`）强行绕过检查。

无论 `if`、`else`、`for`、`while` 代码块只有单行还是多行，必须始终加上大括号 `{}`。

在语法允许时，整数字面量禁止添加小数点（写 `100` 而非 `100.0`）；若语法要求浮点类型但数值为整数，优先使用类型后缀（如 `100d`、`100f`）而非 `.0`。Java 与 C++ 中需自定义指代当前实例的变量名时，优先使用 `thiz` 而非 `self`。

编写涉及网络爬虫或大批量数据处理的脚本（如 Python）时，必须内置进度显示或预计剩余时间（ETA）。
